# Security information and event management (SIEM)

A SIEM is a centralized security platform that collects logs and security events from different systems, networks, firewalls, cloud environments, and applications, analyzes and correlates them, detects suspicious activity, generates alerts, and helps SOC analysts investigate security incidents.

- **Collects** → gathers logs from multiple sources
- **Analyzes** → examines the events
- **Correlates** → connects related events
- **Detects** → identifies suspicious activity
- **Generates alerts** → notifies analysts
- **Investigates** → helps SOC analysts understand and respond to incidents.

# How a SIEM works internally

Log Sources → Collection → Parsing/Filtering → Indexing & Storage → Normalization → Correlation/Detection → Alert → SOC Investigation

### 1. Log Collection — “Get the data”

Logs are generated by different sources:

- Windows/Linux servers
- Firewalls
- EDR
- Applications
- Cloud services
- Network devices

In Splunk, a **Universal Forwarder (UF)** can collect logs from endpoints and send them to Splunk.

**Example:**

```
Windows PC
   ↓
Windows Security Event Log
   ↓
Splunk Universal Forwarder
   ↓
Splunk
```

### 2. Parsing & Filtering — “Clean the data”

The incoming logs may be different formats and may contain unnecessary data.

A processing layer can:

- Parse log fields
- Filter unwanted events
- Remove unnecessary noise
- Mask sensitive information

**Example:**

Raw log:

```
Aug 30 14:20:01 FW01 connection from 192.168.1.50 denied
```

The SIEM can extract:

```
src_ip = 192.168.1.50
action = denied
device = FW01
```

### 3. Indexing & Storage — “Store it so we can search it”

The SIEM stores the processed events in a searchable structure.

In Splunk, this is handled by the **indexer**.

So instead of searching through millions of raw text lines manually, an analyst can search:

```
src_ip=192.168.1.50
```

and quickly find relevant events.

##### 1. Parsing Phase

- The **indexer receives the raw log stream**.
- It breaks the stream into individual **events**.
- It identifies the event's **timestamp** and stores it as `_time`.
- It adds important metadata:
    - **host** → where the log came from
    - **source** → original file/input path
    - **sourcetype** → type/format of the log

Example:

```
Raw Log
   ↓
"Aug 30 14:20:10 FW01 DENY 192.168.1.50"
   ↓
Event
   ↓
_time      = 14:20:10
host       = FW01
source     = firewall.log
sourcetype = cisco:asa
```

##### 2. Bucket Lifecycle

Splunk stores indexed data in **buckets** — directories containing indexed events.

As data gets older, it moves through different bucket states:

```
🔥 HOT → 🟠 WARM → 🧊 COLD → ❄️ FROZEN
```

- **Hot Bucket:**  
    Data is **actively being written**. It is searchable.
- **Warm Bucket:**  
    No longer receiving new data, but it is **still searchable**.
- **Cold Bucket:**  
    **Older data** moved to cheaper/high-capacity storage. It remains searchable according to the deployment's storage configuration.
- **Frozen Bucket:**  
    Data has reached the configured retention limit. It is generally **deleted or archived**, depending on the configuration.

### 4. Normalization — “Make different logs speak the same language”

Different security products use different field names.

For example:

```
Palo Alto → src
Zscaler   → client_ip
AWS       → srcaddr
```

All may represent the **source IP**.

A normalization model such as **Splunk CIM (Common Information Model)** maps them to a common field:

```
src_ip = 192.168.1.50
```

This makes it easier to write detection rules that work across different data sources.

### 5. Correlation & Detection — “Find suspicious activity”

Now the SIEM analyzes events and looks for patterns.

For example:

```
5 failed logins
       ↓
Successful login
       ↓
Login from unusual country
       ↓
Sensitive file accessed
```

Individually, these events may not look extremely suspicious.

Together, they could indicate an account compromise.

The SIEM's detection/correlation rules can recognize this pattern.

### 6. Alerting — “Tell the SOC”

When a detection rule matches suspicious activity, the SIEM generates an **alert**.

Example:

```
🚨 HIGH SEVERITY

Possible Account Compromise

User: john
Source IP: 185.x.x.x
Failed Logins: 20
Successful Login: 1
Sensitive File Access: Yes
```

Now the SOC analyst investigates it.

# SIEM vs EDR

**SIEM** = Looks at security data from the whole environment  
**EDR** = Focuses deeply on individual endpoints

|Feature|**SIEM**|**EDR**|
|---|---|---|
|Full form|Security Information and Event Management|Endpoint Detection and Response|
|Main focus|**Entire environment**|**Endpoints**|
|Monitors|Servers, firewalls, endpoints, cloud, applications, network devices, etc.|Laptops, desktops, servers, etc.|
|Data|Logs and security events|Detailed endpoint telemetry|
|Detection|Correlates events from multiple sources|Analyzes endpoint behavior|
|Investigation|Gives broader attack picture|Gives detailed endpoint/process information|
|Process tree|Usually limited/depends on data source|**Strong capability**|
|Response|Can trigger actions/integrations|Can directly isolate endpoint, kill processes, quarantine files, etc.|
|Example|Correlates login + firewall + cloud + EDR events|Detects `Word → PowerShell → malicious.exe`|
